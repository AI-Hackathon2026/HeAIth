1. Overview

HeAIth guides a user through four steps:

  1. Check-in. The user enters gender, age, height, weight and weekly drinking, smoking and exercise frequency.
  2. Assessment. The server computes BMI, exposure rates for six risk areas, an overall health score (0–100), and a ranking against users of the same age group and gender.
  3. Routine. The user picks a difficulty. Gemini generates a weekly plan with three meals per day (each food with calories) and exercises, plus a short summary and a Markdown report citing pages of the national statistics PDF.
  4. Follow-through. The user ticks off meals and exercises, earns XP to level up a hero avatar, and chats with an AI coach that can rewrite parts of the routine.

Administrators manage the PDF library the AI reads from, browse documents in a page-flip viewer, and can query the KNHANES Excel tables directly.

4. Data storage

JsonStore (src/server/outbound/store/json.store.ts) keeps the whole dataset in one pretty-printed JSON file: data/db.json locally, and the private blob heaith/db.json in Vercel Blob when a Blob store is connected (BLOB_READ_WRITE_TOKEN is set).

  • Reads return deep clones, so callers can never change stored data by accident.
  • Writes run synchronously: mutate in memory, write a temp file, then rename it over db.json. A crash cannot leave a half-written file, and a write cannot interleave with another request in the same process.
  • Freshness: the file's modification time is checked on every access, and the file is reloaded if another process changed it.
  • Relations: the old foreign-key cascades are explicit helpers (deleteUserCascade, deleteRoutineCascade, deleteChatCascade). Unique constraints (email, one routine per user, one health profile per user) are checked in the repositories.
  • Transactions: the UnitOfWork port is kept but runs the work directly. Each repository write is atomic on its own.

Vercel Blob mode

Serverless instances on Vercel do not share a disk, so there the file lives in Vercel Blob. Repositories keep the same synchronous API; the API handler wraps each request:

  1. sync(): before the handler, fetch heaith/db.json with ifNoneMatch (the ETag of the copy in memory). An unchanged file costs a 304 with no body. The pull is skipped while this instance has unsaved changes.
  2. The handler runs against the in-memory copy.
  3. commit(): before the response is returned, save with ifMatch (conditional write). If another instance saved first, the latest file is fetched, this instance's changes since its last sync are replayed onto it row by row (added, changed and deleted rows by id; last writer wins per row), and the save is retried up to five times. Commits within one instance are serialised.
No Blob store connected. The app then falls back to /tmp/heaith, which is private to one serverless instance and wiped when it is recycled, so data appears to vanish between requests. A warning is logged in this case.

5. Documents and statistics data

PDF library

  • Bundled PDFs live in public/documents/ (currently 2024 국민건강통계.pdf, 343 pages) and are served as static files.
  • npm run index:documents extracts each page's text with unpdf (pdf.js). It applies the same Korean text clean-up as v1 and writes data/documents/<name>.json: id (derived from the filename), public URL, and page texts, where page 1 is index 0.
  • Uploaded PDFs (admin, POST /api/files/upload) are stored as <id>.pdf with a <id>.pages.json text file, in data/uploads/ locally or privately under heaith/uploads/ in Vercel Blob.
  • DocumentLibrary merges both sources. The admin PDF viewer asks /api/files/download/:id for a URL: the static file for bundled PDFs, or /api/files/raw/:id for uploads.

KNHANES tables

The 28 Excel workbooks of the 2024 국민건강통계 are in data/knhanes/. KnhanesAdapter finds the 2024 column and the row matching a metric and optional filters (sex, age, income). Only bare .xlsx filenames inside that folder are accepted.

6. Core logic

Health assessment

  • BMI = weight(kg) / height(m)². Obesity status: ≥ 25 obese, < 18.5 underweight.
  • Age groups: 19-29, 30-39, 40-49, 50-59, 60-69, 70+.
  • Exposure rates (%) use 2024 KNHANES prevalence for the user's gender and age group. OBESITY is the full rate if BMI ≥ 25, otherwise 30% of it. HYPERTENSION, DIABETES and STRESS use the group rate. SMOKING is 100 if the user smokes at all. ALCOHOL is 100 at 3+ times a week, 50 at 1–2, else 0.
  • Overall score = 100 − Σ(rate × weight), with weights obesity 0.25, hypertension 0.25, diabetes 0.20, smoking 0.15, alcohol 0.10, stress 0.05.
  • Ranking compares the score with every stored user of the same gender and age group. With no peers it is marked estimated.

Projections

For a disease, the projected rate at difficulty d is current × rate(target days) / rate(current days). Target days are EASY 2, MODERATE 5 and HARD 7 days a week. Exercise frequency is snapped to the buckets 0, 1, 2, 3, 5 and 7.

Progress and gamification

  • Food items, meals and exercises each have a progress value from 0 to 100; 100 means completed. A meal's progress is the aggregate of its food items.
  • Each first completion of a plan item grants 25 XP. planProgressEvents prevents granting the same item twice.
  • Level = floor(xp / 100) + 1, capped at 10. Stages: SPROUT (1–2), GROWTH (3–4), SKILLED (5–7), CHAMPION (8–9), MASTER (10). Level-ups are reported in the response so the UI can celebrate.
  • Daily nutrition composition is computed on the server from the meal foods; Gemini is never asked for percentages.

7. AI pipelines

Health Q&A chat (POST /api/chatbot)

  1. The question is reduced to a primary topic and expanded with Korean synonyms (e.g. 만성질병 ↔ 만성질환, 비만 ↔ 체중/BMI).
  2. Every page of every library document that contains any term is scored. Term matches and statistics markers such as 유병률 or % raise the score; tables of contents and very short pages lower it. The top 6 pages are kept, 2,500 characters each.
  3. With matches, Gemini answers in Korean (해요체) from that context and cites file and page. With none, it falls back to the Gemini File Search store, if one exists, or to a plain answer.
  4. The question and answer are saved as messages of the chat.

Routine generation (POST /api/routines/generate)

  1. Search terms are built from the user's highest exposure risks, and the top 10 matching PDF pages are retrieved.
  2. A structured prompt with profile, risks and difficulty asks Gemini for JSON only: report, reportReadme and a routine entry per day with distinct menus and realistic per-food calories.
  3. The JSON is validated and normalised (three meals per day, calories summed). If the README is missing, a fallback one is written. The result is stored as routine → daily routines → meal plans → food items, plus exercise plans and nutrition summaries.

Routine coach (POST /api/routines/chat/:chatId/message)

The current weekly routine is sent as JSON with the user's request. Gemini returns userMessage, an optional new summary, and dayChanges. Changed days have their meals merged (unchanged meals are kept) or their exercises replaced, and nutrition summaries are recomputed. Plain questions produce no changes.

Models

The default model is gemini-2.5-flash. PATCH /api/chatbot/model switches between the supported Gemini versions, and the choice is saved in settings.geminiModel. Without GEMINI_API_KEY, AI endpoints return 503 while the rest of the app keeps working.

8. Authentication and security

  • Sign-in issues a JWT access token (1 hour) and refresh token (7 days), signed with a built-in secret, in HTTP-only, SameSite=Lax cookies (Secure in production), plus a readable csrfValue cookie. The client retries once through PATCH /api/auth/refresh when a token expires.
  • Refresh tokens are stored hashed and rotated on every refresh. Sign-out clears them.
  • Passwords are hashed with scrypt (random 16-byte salt, 64-byte key, timing-safe comparison). v1 used reversible AES encryption.
  • Roles: USER and ADMIN. File management, user listing and user deletion require ADMIN. The first admin account can be created openly through POST /api/users/signup/admin; after that, creating an admin requires an admin session.
  • Chats are owner-checked on read, update, delete and when sending chatbot messages.
  • Error handling: business errors return their status code and message. Missing resources return 404 and unique conflicts 409. Unexpected errors are logged and return a generic 500.

10. Configuration

The app reads one environment variable, from .env locally or from the Vercel project settings. No AWS, database, Redis, email or OAuth credentials are needed. The token secret and lifetimes (access 1 hour, refresh 7 days) are built into config.util.ts.

VariableDefaultPurpose
GEMINI_API_KEY—Enables AI features
BLOB_READ_WRITE_TOKENadded by VercelSet automatically when a Blob store is connected; switches storage to Vercel Blob

11. Running and deploying

npm install
echo GEMINI_API_KEY=... > .env
npm run dev                    # http://localhost:3000

npm run build && npm start     # production server
npm run index:documents        # after changing public/documents
npm run docs:pdf               # rebuild this document

Vercel: import the repository, add GEMINI_API_KEY, create a Blob store (Storage → Create Database → Blob) and connect it to the project, which adds BLOB_READ_WRITE_TOKEN automatically, then deploy. No build settings need changing. The API route has a 60-second limit, which covers routine generation. The bundled PDF text and Excel tables are traced into the function through outputFileTracingIncludes in next.config.ts.
